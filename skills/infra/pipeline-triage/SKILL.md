# Pipeline Triage（一批）

輸入一個有失敗的 GitHub Actions run，輸出：合併後的根因群 + 每群的負責人 + 開好的 Issue。設計理念見 `docs/infra/pipeline-triage.md`。

> 與 `failure-analysis` 的分工：那支處理**一筆**；這支處理**一批**。80 筆各自分析＝80 倍成本且結論還錯——**必須先合併根因再分析**。
> 後端指令讀 `config/ci-backend-github-actions.md`（讀 run）與 `config/issue-tracker-github.md`（開單）；token 走 env。開單受 `config/governance.yaml` 管制。

## 步驟

1. **收 run**：`gh run view <id> --json jobs,conclusion`、`gh run view <id> --log-failed`；需要報告就 `gh run download <id> -n <artifact>`（Playwright report / junit）。
2. **解析失敗**：每筆取 test id / 檔案 / error signature / 狀態。passed+failed+skipped 應等於 total，不符標 WARNING。
3. **Fan-in 合併（本 skill 的核心）**：把失敗依三維度收斂成根因群——相同 error signature、共同前置步驟、同時轉紅的時間點（CI 版的 bug fingerprint）。
4. **每群分析一次**：對每個根因群呼叫 `failure-analysis` 分類（測試/環境/產品/flaky），**一群一次**，不要逐筆。
5. **分流**：
   - `environment` / stack-wide → **合併成單一 infra issue**，不分派給各 owner。
   - `test-defect` → 交 `test-heal`（若 governance 授權）。
   - `product-regression` → 走產品 bug 流程（`bug-verifier` → `triage`）。
   - `flaky` → 交 `flaky-manager`（quarantine），不開產品單。
6. **分組派工 + 去重**：依 owner（`config` 的 owner_map，查不到用 `git log` 多數作者，再查不到 unassigned 並標註）。一 owner 一單。開單前用 `gh issue list --search` 對 `issues-index.yaml` 去重（同群不重開，改留言）。
7. **開/更新 Issue**：**先把清單（群→根因→owner→要開的單）列給使用者確認**，得同意才呼叫 API。內文開頭加 `> *This was generated by AI during triage.*`，掛 label `ci-triage`。
8. **報告**：輸出表格 `根因群 | 分類 | 影響筆數 | owner | Issue URL(完整) | 動作`，外加 unassigned、collection error、可能 stack-wide 事件提醒。存 `triage-reports/<date>_<run>.md`。

## 鐵則
- **先合併再分析**：省成本、也讓結論正確。
- environment/stack-wide 不分派個人。
- 開單是副作用：先確認、可去重、冪等（同 run 重跑不重開、不重複留言）。
- 只到「開單 + 建議分流」；分析屬 `failure-analysis`、修測試屬 `test-heal`、授權屬 `governance`。
