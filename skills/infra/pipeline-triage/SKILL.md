# Pipeline Triage（一批）

輸入一個有失敗的 GitHub Actions run，輸出：合併後的根因群 + 每群的負責人 + 開好的 Issue。設計理念見 `docs/infra/pipeline-triage.md`。

> 與 `failure-analysis` 的分工：那支處理**一筆**；這支處理**一批**。80 筆各自分析＝80 倍成本且結論還錯——**必須先合併根因再分析**。
> 後端指令讀 `config/ci-backend-github-actions.md`（讀 run）與 `config/issue-tracker-github.md`（開單）；token 走 env。開單受 `config/governance.yaml` 管制。

## 輸入 / 輸出
- **輸入**：run id / run URL（或 `pipeline-read` 已拉好的結構化失敗清單）＋ `config` 的 `owner_map` ＋ `output/issues-index.yaml`。
- **輸出**：根因群清單（每群含分類、影響筆數、owner、issue URL、`assigned_at`）＋ 報告存 `output/triage-reports/<date>_<run>.md`。`assigned_at` 是 `pipeline-observability` 算 `assignment_latency` 的唯一來源，**每群都要有，未派工就寫 `null` 並列進 `unassigned`**。

## 步驟

1. **收 run**：交 `pipeline-read` 拉——它負責 `gh run view --json jobs,conclusion`、`--log-failed`、必要時 `gh run download`，並照「由粗到細」省 token。**不要自己重刻一套讀法。**
2. **接結構化失敗清單**：直接吃 `pipeline-read` 的輸出（每筆已含 nodeid / 檔案 / 正規化過的 error signature / job）。它回報的 `count-mismatch` warning 要原樣帶進本次報告。
3. **Fan-in 合併（本 skill 的核心）**：把失敗依三維度收斂成根因群——相同 error signature、共同前置步驟、同時轉紅的時間點（CI 版的 bug fingerprint）。
4. **每群分析一次**：對每個根因群呼叫 `failure-analysis` 分類（測試/環境/產品/flaky），**一群一次**，不要逐筆。
5. **分流**：
   - `environment` / stack-wide → **合併成單一 infra issue**，不分派給各 owner。
   - `test-defect` → 交 `test-heal`（若 governance 授權）。
   - `product-regression` → 走產品 bug 流程（`bug-verifier` → `triage`）。
   - `flaky` → 交 `flaky-manager`（quarantine），不開產品單。
6. **分組派工 + 去重**：依 owner（`config` 的 owner_map，查不到用 `git log` 多數作者，再查不到 unassigned 並標註）。一 owner 一單。開單前用 `gh issue list --search` 對 `output/issues-index.yaml` 去重（同群不重開，改留言）。
7. **開/更新 Issue**：**先把清單（群→根因→owner→要開的單）列給使用者確認**，得同意才呼叫 API。內文開頭加 `> *This was generated by AI during triage.*`，掛 label `ci-triage`。
8. **報告**：照下面的格式存 `output/triage-reports/<date>_<run>.md`，並把同一份表列給使用者。

## 鐵則
- **先合併再分析**：省成本、也讓結論正確。
- environment/stack-wide 不分派個人。
- 開單是副作用：先確認、可去重、冪等（同 run 重跑不重開、不重複留言）。
- 只到「開單 + 建議分流」；分析屬 `failure-analysis`、修測試屬 `test-heal`、授權屬 `governance`。

## 輸出（格式，非某次執行結果）
```yaml
# output/triage-reports/<date>_<run>.md 內嵌的 front matter
run: "https://github.com/<owner>/<repo>/actions/runs/1234567890"
triaged_at: 2026-07-29T10:40:00Z
groups:
  - signature: "locator([data-test=apply-coupon]) timeout at <line>"
    category: test-defect        # test-defect | environment | product-regression | flaky
    affected: 14                 # 這群涵蓋幾筆失敗
    owner: "<github handle>"     # 查不到寫 null
    assigned_at: 2026-07-29T10:41:00Z   # 未派工寫 null
    issue: "https://github.com/<owner>/<repo>/issues/512"
    action: "交 test-heal"
unassigned: []                   # owner 查不到的群,要人接手
warnings:                        # 原樣帶 pipeline-read 的 count-mismatch
  - code: count-mismatch
    detail: "疑似 shard 4 未回報"
stack_wide_suspected: false      # 多群同時轉紅 → 可能是單一 infra 事件
```
一行摘要：**幾群、幾筆、幾張單、幾群 unassigned。**

## 上下游
上游：`pipeline-read`（結構化失敗清單）、使用者貼 run URL、`pipeline-observability`（mttr / 派工延遲超標時路由過來）。下游：`failure-analysis`（每群分類）、`test-heal`（test-defect）、`bug-verifier` → `triage`（product-regression）、`flaky-manager`（flaky 群）、`pipeline-observability`（讀 `output/triage-reports/` 算 `assignment_latency`）。
