# Bug Fixer

輸入過了 gate 的 Issue、證據及交接識別，輸出待 review 的 PR。先讀 `references/agent-handoff.md`、`references/config-resolution.md` 與 `references/agent-governance.md`；後端讀該 project 的設定，本地 Issue 依交接路徑讀取。設計理念見 `docs/agents/bug-fixer.md`。

> **順序就是紀律：先重現、先寫會紅的測試、才改碼。** 測試轉綠不是目的，行為對了才是。

## 前置（缺了就停手回報）

- Issue 對應相同 `(project, session, finding_id)` 的 gate pass，範圍清楚且根因可及；影響面不明就交人判。開單後 index 出現自身 Issue 不表示要重跑新單閘門。
- 產品 repo 可存取、測試可本地跑；核對產品 repo 與 PR 目標，不把 Issue tracker repo 自動當成產品 repo。用 GitHub 讀 Issue 或開 PR 時才檢查登入；沒有 PR 後端時先交付本地修復與驗證結果。
- 全域 governance 可讀且 `merge_pr` 在 forbidden。改測試、產品碼、push、開 PR、留言與標籤更新各自檢查對應權限，不以開 PR 的確認補授權前面的修改。

## 執行順序（不得跳號、不得倒序）

1. **重現**：照 Issue 步驟跑一次，UI／API 留證依交接契約。跑不出來就交回說明；要留言或改標籤時，分別先檢查 `comment_issue`／`update_issue`，無權限就只回報使用者。
2. **寫紅測試**：先確認 `edit_tests` 授權、讀解析後的 `test-style.md`（缺檔沿用 `references/test-design.md`），再加一個現在就會紅的回歸測試，驗證「使用者看到的行為」。跑一次，確認它有紅、且紅的原因就是這顆 bug。
3. **最小修改**：先確認 `edit_product` 授權，再改最小幅度的產品碼；不順手重構、不動無關檔案。
4. **轉綠驗證** — 新測試轉綠，**且整套既有測試沒被弄壞**。
5. **開 PR**：備好 title、diff 摘要、Issue 連結、重現步驟、根因與修法。推送前查 `push_branch`，建立 PR 前查 `create_pr`；授權涵蓋目標與範圍就沿用，否則確認。明確指定產品 repository 與分支，內文開頭加 `> *This was generated by AI during bug-fixing.*`，標 ready-for-review。
6. **回報**：附完整 PR URL、測試與產品檔案、先紅後綠證明；PR 因後端或權限未建立時，交付本地 diff 與具體原因，不宣稱已開 PR。

## 鐵則

- **無法重現，就不能修。** 這條和 triage 的「無法重現不開單」同源，不容例外。
- **絕不 merge。** 開 PR 是上限；merge 是人按的（`governance.yaml` forbidden 釘死，不靠自律）。
- **防綠色作弊**：禁項清單見 `references/green-cheating.md`，一條都不准踩。
- 一張 Issue 一個 PR，一個 PR 只修一件事。
- 測試先紅後綠缺一段都不算：沒紅過的測試證明不了 bug 存在，沒轉綠的修復證明不了修好了。

## 驗收（跑完自己對一次）

- 動手前**有先重現**嗎？（重現不了有退回，而不是硬改？）
- 回歸測試**先紅後綠**、驗的是行為嗎？
- 產品碼改動是**最小**、既有測試全綠嗎？
- PR 已開時是否附 AI 聲明且沒 merge；未開時是否如實留下原因？
- 每個副作用是否有對應授權，且交付報告記下 project、session、finding_id 與授權來源？
