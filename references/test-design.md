# 測試設計原則（reference，被 test-author / api-test-author / test-heal / test-prune 讀）

一支自動化測試的價值不是「它會跑」，而是**它壞掉的時候，有人看得懂、而且值得去看**。下面每一條都是為了這件事。

## 0. 先選層級：這條驗收條件該在哪一層驗

寫測試之前先問一句：**這條規則住在哪一層。** 選錯層級的測試，就算寫得再漂亮，也是拿貴的工具去驗便宜的東西。

| 這條 AC 在講什麼 | 該在哪一層驗 | 為什麼 |
|---|---|---|
| 商業規則、計算、驗證、權限（折扣怎麼算、誰能看誰的資料）| API | 規則住在後端。用畫面驗，等於把渲染、載入、定位器全綁進失敗面 |
| 畫面呈現、互動、可及性（錯誤訊息有沒有顯示在對的地方）| UI | 這條規則真的住在畫面上 |
| 前後端接起來會不會壞（送出去的欄位對不對、回來的資料有沒有顯示）| UI，但只挑一條代表路徑 | 這是整合風險，一條就夠，不需要每個分支都走一遍 |

實務上的取捨：同一條規則的**分支**（折扣碼過期、額度不足、幣別不同、疊加上限）全部在 API 層寫，UI 只留一條把主線接起來的測試。反過來做，就是十支慢又脆的 UI 測試在驗一件後端的事。

判斷不了時的預設：**能在 API 驗就在 API 驗**。它快一個數量級、失敗訊息指得準、不會因為改版位而紅。成本面的理由見 `sdet-economics`，要不要測則交 `route-by-risk`。

## 1. 一支只驗一件事
一條驗收條件對一支測試。串成長流程的測試，紅了只能告訴你「這條路上某處壞了」，不能告訴你壞在哪；而且前段一壞，後段全部失去意義。
要驗兩件事就開兩支。重複的前置步驟交給 fixture，不是把斷言疊在一起。

## 2. 名稱寫「使用者看到什麼」，不是「你點了什麼」
測試名稱是失敗報告的第一行，也常常是唯一一行被讀到的。
- ○ `套用折扣碼後顯示折後金額`
- × `點擊 apply 按鈕`、`test_checkout_2`

實作步驟會改（按鈕換位置、流程多一頁），使用者可見的結果不會。用結果命名，測試的意圖就不會隨介面改版而失傳。

## 3. 定位器優先序
1. **測試專屬屬性**（`data-test` 之類，實際名稱由專案設定決定，不寫死在原則裡）。它存在的唯一理由就是被測試用，改版時大家知道不能亂動。
2. **角色／可見文字**：貼近使用者實際怎麼找到這個東西，順帶驗了可及性。
3. 其他。

**絕不用**：結構性 CSS（`div:nth-child(1)`、`.container > div > span`）、深層 XPath、框架自動產生會變動的 ID。這類定位器不是「比較脆弱」，而是**它壞掉時你根本不知道是產品壞了還是版面挪了**。

## 4. web-first assertion，禁止固定 sleep
會自動重試的斷言（等到條件成立或逾時）才是正確的等待方式。
固定 sleep（`waitForTimeout`）有兩個問題：機器慢的時候它還是不夠久（flaky），機器快的時候它白等（慢）。更糟的是，它把「等什麼」這個資訊藏起來了。後人只看到一個 2000，不知道在等誰。
**沒有任何一次「加 sleep」是修好，那是把時序問題蓋住。**

## 5. 不硬編會變動的資料
商品名、價格、庫存、自動產生的 ID 都會變。硬編等於把測試綁在某一份資料快照上。
做法：從畫面或 API **讀出來**，再拿讀到的值去比對（例如：先讀商品頁價格，再驗購物車金額等於它）。這樣驗的是「一致性」這個真正的規則，而不是「當時剛好是 990」。

## 6. 斷言帶意圖訊息
斷言要附一句「應該是什麼」，讓失敗訊息自己會說話：讀的人不看程式碼就知道預期。
禁止廢斷言（`expect(true).toBe(true)`）、禁止為了讓它過而放寬（`toBe` 改成 `toBeTruthy`、拿掉關鍵欄位）。那是綠色作弊。

## 7. 測試獨立：自備、自清
每支測試自己建它要的資料、自己在 teardown 清掉，且**失敗時也要清到**。
不依賴執行順序、不依賴「環境裡本來就有的那筆」、不共用可變狀態。這三件事是平行執行下 flaky 的主要來源。

## 8. 這支測試值不值得存在
新增前、定期回顧時都問一次：
- 它驗的行為**還存在嗎**？
- 它**跟別支重複嗎**（有沒有獨有的斷言）？
- 它壞掉時**你會不會真的去看**？

三題有一題答不出來，這支就是噪音而不是安全網。要淘汰時，先寫清楚「刪掉之後失去什麼覆蓋」，而且**不准用刪測試來解決一支會紅的測試**。

## 9. API 測試怎麼對應上面這幾條

第 1、2、5、6、7、8 條照舊，一個字都不用改。第 3 條（定位器）與第 4 條（web-first assertion）是畫面專屬的，API 測試沒有元素可定位、也沒有渲染要等，對應的位置換成下面兩條：

- **第 3 條的對應：斷言綁契約，不綁欄位順序或整包快照。** 驗「該有的欄位在、型別對、值符合規則」，不要把整份回應序列化下來當黃金檔比對。整包快照等同於結構性 CSS：後端多加一個無關欄位就紅，而讀失敗訊息的人不知道是產品壞了還是回應多長了一格。有契約來源就用 schema 驗，沒有就逐欄位寫明。
- **第 4 條的對應：等狀態而不是等時間。** 非同步流程（送出後背景處理、佇列、webhook）要輪詢到終態才判定，逾時就失敗，一樣禁止固定 sleep。這跟第 4 條是同一個道理：藏起來的是「在等什麼」。

另外兩件 API 測試特別容易做錯的事：
- **狀態碼與 body 兩個都要驗。** 只驗 `200` 的測試，遇到「`200` 包著錯誤訊息」會安穩地綠。
- **測資走 API 建、測資也走 API 清**（交 `test-data`），但**不要用被測的那個端點來準備它自己的前置資料**。那樣它一壞，測試會以「前置失敗」的形式報錯，看不出真正壞的是誰。
