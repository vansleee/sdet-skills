# workflow/（把 SDET 接進團隊/SDLC）

`skills/workflow/` 每支 skill 的設計理由。執行指令在各自的 `SKILL.md`，這裡只寫為什麼。

## test-planning

把一張 ticket 變成「這輪測什麼、不測什麼、為什麼」。

### 設計理念
- **產出是決定，不是 test case 清單。** 傳統 test plan 的失敗模式是寫出 60 條步驟，然後沒人照著跑、也沒人維護。本 skill 只產出「範圍 + 風險 + 每項用什麼形式測」，把「怎麼走」留給 `explore`（開放路徑）、把「逐步腳本」留給 `test-author`（要長期守的回歸）。
- **out-of-scope 必須寫理由。** 這是整支 skill 最容易被省略、也最值錢的一欄。「沒測到」和「評估後決定不測」在事後看起來一模一樣，但意義完全相反。三個月後出事時，有理由的那份能回答「當時我們知道，並且判斷風險可接受」，沒理由的那份只能回答「不知道」。這和 `route-by-risk` 的「skip 不是丟掉，是留痕」是同一條紀律在不同層級的展開。
- **風險評分委外，不自己發明。** 若 planning 自己長出一套風險判準，就會和 `route-by-risk` 給出不同答案，而人會挑對自己方便的那個。單一評分來源是刻意的約束。
- **規格衝突要在規劃階段就標出來。** 需求和 `projects/<project>/knowledge/` 打架時，最貴的處理方式是測到一半才發現。那時已經投入了探索成本，而且會產出一批無法判定的 finding。提早標成 `spec-conflict`，等於把 `test-oracle` 的判準問題前移到最便宜的時點。
- **知識缺口要明說「基於假設」。** agent 最危險的行為是用合理推測填補 `projects/<project>/knowledge/` 的空白，然後把推測當事實往下游傳。明寫出來，才有人會去補 `projects/<project>/knowledge/`。
- **吃 traceability 的 gap 回饋。** planning → 執行 → traceability → 下一輪 planning，這條迴圈讓「上次漏掉的」有機會回到這次的候選清單，而不是永遠留在報表上當紅字。

## api-coverage-matrix

把一份 API 設計文件展開成一張逐端點、逐方法、正負向情境的優先序案例矩陣。

### 設計理念
- **跟 test-planning 警告的「60 條步驟」不一樣。** `test-planning` 的文件明講傳統 test plan 的失敗模式：寫出一長串步驟，沒人照著跑、也沒人維護。本 skill 的產出不是操作手冊，是**需求清單**：每一列是一個可獨立驗證的斷言單位，近似 `traceability` 的 `req_id`，附優先序與覆蓋狀態，給人審閱、給下游排工，不是給人逐步照做。真正要長期守的回歸，一律由 `api-test-author` 一支一支固化成程式碼；本 skill 產出的是那條自動化待辦清單的來源，不是取代它。
- **優先序跟 route-by-risk 的分數回答不同問題。** `route-by-risk` 回答「這個東西值不值得測」，輸出 `must-test`／`sample`／`skip`。本 skill 的 P0～P3 只在「已經判定要枚舉」的前提下，回答「這些案例裡哪個先做、哪個先自動化」。兩者疊在同一張表上會出現「兩個答案，各自方便各自用」的問題，所以刻意分層：範圍交 `route-by-risk`／`test-planning`，順序才是本 skill 的事。
- **橫切構面用抽查，不用窮舉。** RBAC/LBAC 的角色 × 資源矩陣、旗標開關組合、audit log，這些機制本身通常已經有共用的測試在守。本 skill 只驗「這個端點有沒有正確接上那套共用機制」，不是重新驗證機制本身，否則案例數會隨端點數線性爆炸，而且大多數案例在驗同一件事。
- **查不到覆蓋就是 Gap，不用推測。** 這條紀律照抄 `traceability`：灌水的覆蓋比沒有覆蓋更危險，會讓人誤以為有安全網。既有自動化測試清單要主動問人或給清單，不用「應該測過」的合理推測填。
- **憑證只留佔位符。** 這份矩陣通常要分享給非技術關係人審閱或簽核，cURL／payload 範例最容易被順手貼上真實金鑰再轉發出去。一律用 `<TENANT>`／`<API_TOKEN>`，要做本機代填的互動版本，值只能留在瀏覽器端，不外送、不落地檔案。
- **三種輸出格式，一份事實來源。** csv／xlsx／html 服務不同讀者（版控 diff、Excel 簽核、瀏覽器審閱），但欄位定義只能存在一個地方；手動改其中一份，格式之間就會慢慢長歪，沒人發現。

## traceability

需求、測試、finding 三者的對照，以及**刻意不做的那幾件事**。

### 設計理念
- **不算單一覆蓋率百分比。** 這是本 skill 最重要的一個「不做」。任何被印在報表上的覆蓋率數字，都會在幾週內變成 KPI；而衝高它最便宜的方法是寫沒有斷言價值的測試。輸出對照表與 gap 清單，讓人看見「哪一條沒人守」，比看見「守了 82%」有用得多。前者能行動，後者只能討論。
- **不猜對應，`uncertain` 不計入 covered。** 靠檔名語意推測出來的對應是猜測。把猜測算成覆蓋，等於製造假的安全網：報表說有測，實際上沒有，而且沒有任何一刻會有人發現。標成 `uncertain` 反而會推著專案往「測試自己宣告 req_id」遷移，那才是真正的修法。
- **測試孤兒不等於該刪。** 對不到需求有兩種可能：測試多餘，或 `projects/<project>/knowledge/` 漏寫了這條需求。直覺會選第一種（刪比較快），但第二種很常見，尤其在 `projects/<project>/knowledge/` 還在長的專案。所以流程刻意規定先問「是不是需求沒寫」，再談 `test-prune`，而 `test-prune` 本身也只給建議。
- **finding 孤兒是好消息。** 找到規格沒寫的行為，正是自主探索的價值所在。把它標成孤兒不是為了扣分，是為了把它變成「補 `projects/<project>/knowledge/`」的待辦，讓探索的收穫累積成下一輪的判準。
- **`req_id` 不可回收。** 換號會讓既有對應安靜地斷掉，而斷掉時沒有任何錯誤訊息。需求下線就標 `retired`、保留 id。
- **規則放 reference，資料放狀態檔。** 對應規則會隨專案演進（從檔名推測 → tag → annotation），把它寫進 `output/traceability.yaml` 會讓演算法和資料混在一起，改規則就得改資料。
- **這條回饋邊讓規劃變準。** gap 清單回到 `test-planning`，讓「上次漏掉的」有機會進入這次候選，而不是永遠留在報表上當紅字。

## status-report

把散在各狀態檔的事實，講成一段人看得懂的話。

### 設計理念
- **只彙整，不重算。** 這是本 skill 的存在前提。flaky rate 的真相在 `output/flaky-registry.yaml`、放行的真相在 `output/pipeline-gate.yaml`、覆蓋的真相在 `output/traceability.yaml`。報告若自己重算一次，團隊就會有兩個版本的數字，然後在會議上花時間爭論哪個對，而兩個都是對的，只是算法不同。單一真相比精確更重要。
- **缺資料寫「無資料」，不填 0。** 報告是最容易發生「用合理數字填空」的地方，因為空白看起來不專業。但把「本期沒跑 traceability」寫成「覆蓋 100%」，是把沒量到偽裝成沒問題。這條紀律和 `route-by-risk`、`pipeline-observability` 是同一條。
- **每個結論附出處。** 報告會被追問（「這個 bug 確定嗎」「這數字哪來的」）。掛上狀態檔路徑或 URL，追問就變成點一下連結，而不是重跑一次分析。
- **隔離中的測試必須講。** 它不好看，所以最容易被省略；但「這期有 3 支測試是關掉的」正是讀者判斷風險時最需要的一句話。省略它，報告就從摘要變成公關稿。
- **`release-readiness` 不下裁決。** 它是 `release-signoff` 的輸入。若報告自己說「可以出」，就會出現「報告說可以、簽核說不行」的矛盾，而人通常會採信先看到的那個。所以刻意限制成只陳述現況。
- **三種格式對應三種讀者。** standup 的讀者要的是「有沒有事需要我做」，測試報告的讀者要的是證據，release-readiness 的讀者要的是決策素材。同一份內容塞給三種人，三種人都不會看。

## release-signoff

「這一版能不能出？」：三層閘門的最上層。

### 設計理念

- **三層閘門，上層吃下層的產物。** `issue-quality-gate`（一張單）→ `infra/quality-gate`（一個 build）→ 本 skill（整個 release）。每層問的問題不同，且上層不重跑下層。若本層自己再跑一次測試，會得到和 `output/pipeline-gate.yaml` 不同的結果，接著沒有人知道該相信哪一個，而人通常會相信比較綠的那個。
- **下層的 OVERRIDE 不會在上層自動變綠。** 這是刻意設計的防漏：`quality-gate` 允許人硬推（現實需要出口），但硬推的理由必須一路浮到 release 層被再看一次。否則「build 層硬推 → release 層看到 PASS → 簽出去」就成了一條把 override 洗白的路徑。
- **`inconclusive` 不得當 pass。** 拿不到 `output/traceability.yaml`、artifact 過期、指令失敗。這些最容易被當成「沒發現問題」。但閘門的價值全在它擋住的那幾次，而那幾次往往正是證據殘缺的那幾次。
- **只評估，不執行；簽核人是人。** 本 skill 不打 tag、不 deploy、不 merge。`signed_by` 由人填，報告開頭明標「AI 彙整，決定屬於人」。理由不是技術限制，而是一個能自己判「可以出」又能自己出的 agent，錯誤成本沒有任何緩衝。
- **`conditional-go` 的條件必須可檢查。** 現實中很多 release 是「知道有風險但仍要出」。堵死這條路只會逼人繞過整個流程。所以給出口，但條件要寫成可驗證的句子：「上線後 24h 內錯誤率 > 1% 即回滾，由 X 監控」而不是「小心一點」。前者是承諾，後者是心情。
- **`no-go` 必附補完清單。** 一句「不能出」把問題丟回給團隊；一份「缺這兩項、誰補、約兩天」讓否決變成可執行的計畫。閘門要能擋，也要能指路。
- **關掉的覆蓋寫進正文，不放附註。** 「有 9 支測試被隔離」是簽核者判斷風險的關鍵事實。放進附註等於希望沒人看到。
