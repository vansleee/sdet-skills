# Test Planning
把一張 ticket 變成「這輪測什麼、不測什麼、為什麼」。

## 設計理念
- **產出是決定，不是 test case 清單。** 傳統 test plan 的失敗模式是寫出 60 條步驟，然後沒人照著跑、也沒人維護。本 skill 只產出「範圍 + 風險 + 每項用什麼形式測」，把「怎麼走」留給 `explore`（開放路徑）、把「逐步腳本」留給 `test-author`（要長期守的回歸）。
- **out-of-scope 必須寫理由。** 這是整支 skill 最容易被省略、也最值錢的一欄。「沒測到」和「評估後決定不測」在事後看起來一模一樣，但意義完全相反。三個月後出事時，有理由的那份能回答「當時我們知道，並且判斷風險可接受」，沒理由的那份只能回答「不知道」。這和 `route-by-risk` 的「skip 不是丟掉，是留痕」是同一條紀律在不同層級的展開。
- **風險評分委外，不自己發明。** 若 planning 自己長出一套風險判準，就會和 `route-by-risk` 給出不同答案，而人會挑對自己方便的那個。單一評分來源是刻意的約束。
- **規格衝突要在規劃階段就標出來。** 需求和 `knowledge/` 打架時，最貴的處理方式是測到一半才發現。那時已經投入了探索成本，而且會產出一批無法判定的 finding。提早標成 `spec-conflict`，等於把 `test-oracle` 的判準問題前移到最便宜的時點。
- **知識缺口要明說「基於假設」。** agent 最危險的行為是用合理推測填補 `knowledge/` 的空白，然後把推測當事實往下游傳。明寫出來，才有人會去補 `knowledge/`。
- **吃 traceability 的 gap 回饋。** planning → 執行 → traceability → 下一輪 planning，這條迴圈讓「上次漏掉的」有機會回到這次的候選清單，而不是永遠留在報表上當紅字。
