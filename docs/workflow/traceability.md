# Traceability
需求、測試、finding 三者的對照——以及**刻意不做的那幾件事**。

## 設計理念
- **不算單一覆蓋率百分比。** 這是本 skill 最重要的一個「不做」。任何被印在報表上的覆蓋率數字，都會在幾週內變成 KPI；而衝高它最便宜的方法是寫沒有斷言價值的測試。輸出對照表與 gap 清單，讓人看見「哪一條沒人守」，比看見「守了 82%」有用得多——前者能行動，後者只能討論。
- **不猜對應，`uncertain` 不計入 covered。** 靠檔名語意推測出來的對應是猜測。把猜測算成覆蓋，等於製造假的安全網：報表說有測，實際上沒有，而且沒有任何一刻會有人發現。標成 `uncertain` 反而會推著專案往「測試自己宣告 req_id」遷移，那才是真正的修法。
- **測試孤兒不等於該刪。** 對不到需求有兩種可能：測試多餘，或 `knowledge/` 漏寫了這條需求。直覺會選第一種（刪比較快），但第二種很常見——尤其在 `knowledge/` 還在長的專案。所以流程刻意規定先問「是不是需求沒寫」，再談 `test-prune`，而 `test-prune` 本身也只給建議。
- **finding 孤兒是好消息。** 找到規格沒寫的行為，正是自主探索的價值所在。把它標成孤兒不是為了扣分，是為了把它變成「補 `knowledge/`」的待辦——讓探索的收穫沉澱成下一輪的判準。
- **`req_id` 不可回收。** 換號會讓既有對應安靜地斷掉，而斷掉時沒有任何錯誤訊息。需求下線就標 `retired`、保留 id。
- **規則放 reference，資料放狀態檔。** 對應規則會隨專案演進（從檔名推測 → tag → annotation），把它寫進 `output/traceability.yaml` 會讓演算法和資料混在一起，改規則就得改資料。
- **這條回饋邊讓規劃變準。** gap 清單回到 `test-planning`，讓「上次漏掉的」有機會進入這次候選，而不是永遠留在報表上當紅字。
