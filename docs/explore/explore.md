# Explore

依 charter 自主探索：自己決定下一步、記路徑、留證，產出候選 findings。

## 設計理念
- **自主的心臟，也是最容易翻車的地方。** LLM agent 放手後三大失敗模式：亂點、鬼打牆、幻覺。本 skill 的價值不在「會點」，而在用三條硬規則把這三件事擋掉。
- **下一步必須引用當前畫面證據** → 防亂點（不能憑空決定）。
- **路徑記憶，做過不重做** → 防鬼打牆。
- **沒證據不喊 bug** → 防幻覺；判定外包給 `test-oracle` / `classify-anomaly`，探索只負責「看與試」。
- **一定要有停止條件。** 達標 / max_steps / 偵測打轉就停，不無限探索。
- **charter 決定邊界。** out-of-bounds 硬守，遇到就停手回報。

## 覆蓋鐵則怎麼來的

三大失敗模式（亂點、鬼打牆、幻覺）管的是「探索會不會失控」。跑過真實 session 才發現，探索**沒失控但漏看**是另一種失敗，而且更難察覺：探索自己會宣告「charter 範圍走完」，看起來像收工，實際上只覆蓋了三分之二。

2026-08-01 對 academybugs.com 那輪給了難得的校準機會。那站是練習站，站方公告植入 25 支 bug 並自帶確認機制，等於現成的外部判準。對照結果：探索兩輪獨立命中 17 支（召回率 0.68），另外抓到 12 支站方沒計分的真缺陷。判斷力不差，漏掉的 8 支追下去，成因收斂成四個根因。

**根因一：oracle 是相對的，整批一起錯就沒有訊號。**
charter 的 oracle 幾乎都是內部一致性（列表價格等於內頁價格、卡片標題等於內頁標題）。這種判準靠互相比對產生訊號。那輪量了 18 張列表圖，抓到唯一被壓扁的那張，卻漏掉 14 張一致地沒填滿容器的：一致，所以比對無異常，看起來就像設計決定。同一個 oracle 抓得到一個離群，抓不到十四個共犯。
→ 每條相對判準配一條絕對判準。

**根因二：靜態解析取代了互動。**
為了在 `max_steps` 內覆蓋 18 個商品，探索改用 `fetch` 加 DOMParser 比對。便宜、可規模化，但只看得到 HTML 的初始狀態。最能說明問題的是那顆 Twitter 分享鈕：`href` 是完全正常的 `twitter.com/intent/tweet`，屬性檢查一定放行，事件處理器攔截後才改開拼錯的網域。同一排分享鈕上的 MySpace 被抓到了，因為它的 `href` 本身就爛。
→ 靜態解析只用來選目標，不用來下結論。

**根因三：把「動作被接受」當成「動作成功」。**
`checked_and_ok` 裡寫著「編輯表單可載入、可送出」，於是結案。實際上送出後 loader 永遠轉、資料沒存。通過條件停在送出那一刻，沒等終態。
→ 通過條件寫到終態。

**根因四：狀態空間只走單軸。**
每個控制項都在最順手的那個頁面或商品上測一次。色票在 A 商品測、數量在 B 商品測，兩個變因從沒交叉，於是「選特定顏色後加數量會凍住」漏掉。同樣的偏誤讓價格篩選只在列表頁驗過就記成 OK，沒回頭測商品頁側欄的同一組控制項。延伸出來的是可見性問題：收合的元件、主流程沒連過去的頁面，因為 charter 的 scope 寫成功能區塊而非 URL，被隱含涵蓋而整條沒走。
→ 控制項換頁重測、變因交叉配對，並把沒被端出來的東西列進計畫。

## 為什麼停止條件要一起改

這四條鐵則解決的是「漏什麼」，但探索當時並不知道自己漏了。它的 `stop_reason` 寫「charter 範圍走完」，而範圍是自己定義的。沒有外部判準時，「走完」只能是自我宣告，而它的自信來源正是 `checked_and_ok` 那份清單，其中兩條恰好就是根因三的漏檢點。

所以停止條件要求把鐵則自檢的結果寫進 `stop_reason`：說得出哪幾條過了、哪幾條沒過，比宣稱「走完」有用。

上游：`exploration-charter`（給目標與邊界）。下游：`structured-result`、`classify-anomaly`、`bug-verifier`。
