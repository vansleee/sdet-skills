# Test Oracle
用一致性/規格/對照/使用者期待等 oracle 判斷「這到底是不是 bug」。

## 為什麼 API 要另開一張 oracle 表

不是因為 API 比較特別，是因為**畫面層的三條免費 oracle 在 API 上會失效**。沒有畫面就沒有「同一畫面自相矛盾」，沒有瀏覽器就沒有 console error，而「API↔UI 一致」這條在只有 API 的情境下沒有另一半可比。剩下的若只有規格 oracle，等於沒有 spec 就什麼都判不動，探索會整批卡在 `needs-spec`。

補上的那幾條，共通點是**判準內建在協定或在回應自身**，不必外求：HTTP 狀態碼有公認語意、同一個 API 的錯誤結構該長一樣、宣告冪等的方法重打該同結果、換個 id 不該拿到別人的資料。它們補回「不需外部資訊」那一格，強度才跟 UI 情境對得起來。

## 契約 oracle 為什麼排在後面

schema 符合是很好判的 oracle，但它需要一份 OpenAPI，而**契約本身也可能是錯的或過期的**。契約說回 `200`、實際回 `200` 但語意荒謬，契約 oracle 會判過。所以排序上讓不靠外部檔案的幾條先跑，契約當補強而不是唯一判準。契約來源填「無」時直接停用它，不允許用「我覺得該有這個欄位」冒充 schema。

## `4xx` 的陷阱

API 探索最常見的假 bug 是把 `400` 與 `401` 當成發現。那通常是產品正確地拒絕了亂打的請求。真正要判的是兩個方向的錯：該擋沒擋（越權拿到資料、非法值被接受），與該過卻擋（合法請求被拒）。`429` 則先當自己打太快，對照 `product-context.md` 記的速率限制再說。
