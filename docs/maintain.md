# maintain/（顧好每一支測試）

`skills/maintain/` 每支 skill 的設計理由。執行指令在各自的 `SKILL.md`，這裡只寫為什麼。

## test-author

把一條驗收條件（或一次成功探索）固化成一支可維護的 Playwright 測試。

### 設計理念
- **寫測試是負債不是資產。** 每多一支就多一份要養一輩子的東西。所以重點不是「產得快」，而是「產出的那一支值得留」。交付前先問「跟現有測試重複嗎」，重複就不要寫。
- **user-invoked 是刻意的。** 該不該多一支測試是人的權衡（覆蓋 vs 維護成本），不該讓模型在背景自行新增；這就是 `disable-model-invocation: true` 的理由。
- **名稱寫結果、不寫操作。** 失敗報告上通常只有測試名稱會被讀到。用「使用者看到什麼」命名，測試的意圖才不會隨介面改版失傳。
- **定位器與等待方式是 flaky 的兩大源頭。** 所以在寫的當下就要求穩定定位器與 web-first assertion，而不是等它開始間歇紅再回頭救。那時要付 `flaky-detect` ＋ `test-heal` 兩次錢。
- **交付前的紅綠驗證。** 故意把預期改錯要紅、改回要綠。只會綠的測試等於沒在測。這和 `test-heal` 的驗收是同一條標準，只是提前到出生時做。
- **邊界。** 測資交 `test-data`、修既有測試交 `test-heal`、該不該留交 `test-prune`。共用判準集中在 `references/test-design.md`，不各寫一份。

## api-test-author

`test-author` 的姊妹 skill。同一件事（把一條規則固化成一支養得起的測試），換一個介面層做。

### 為什麼分開，而不是給 test-author 加一個模式

`test-author` 的五條紀律裡有兩條是畫面專屬的：定位器優先序、web-first assertion。這兩條佔了它一半的份量，而且是它最常被引用的部分。API 測試裡沒有元素可定位、沒有渲染要等，硬塞進同一支 skill，會變成「第 3、4 條看情況適用」。**一份會說「看情況」的紀律，等於沒有紀律。**

分開之後，兩支各自的第 3、4 條都能寫死，而共通的第 1、2、5、6、7、8 條留在 `references/test-design.md` 由兩邊共讀。真正的原則只有一份，不會分岔。

### 為什麼一定要先確認層級

這支 skill 最大的價值其實不在「怎麼寫」，在於它逼人先問「這條規則住在哪一層」。實務上最常見的浪費是：後端的商業規則，被寫成十支 UI 測試去驗它的十個分支。每一支都要開瀏覽器、登入、走到那一頁，然後驗一件跟畫面無關的事。這種測試慢、脆、失敗訊息還指不準，改個版位就整批紅。

所以流程裡有一步是「已經有 UI 測試在驗同一條規則的話，這不是新增，是搬家」，搬完要回頭評估上面那支該不該留。少了這一步，加了 API 測試只會變成覆蓋兩份、維護兩份。

### 為什麼禁止整包快照比對

回應快照（把整份 JSON 存成黃金檔）寫起來最快，也最容易讓人以為驗得很徹底。但它把「這個欄位該是什麼」換成了「整包跟上次一樣」，後端多加一個無關欄位就整批紅，而失敗訊息只會說有差異，不會說差在哪條規則。

這跟 `test-author` 禁止結構性 CSS 是同一個判斷：**壞掉的時候分不出是產品錯了還是外形變了，這種斷言就不該用。**

### 為什麼權限測試要求寫兩支

「本人拿得到」跟「別人拿不到」感覺是一件事的兩面，實際上只有後者在驗授權。只寫前者的測試，在授權整個失效的情況下照樣是綠的，因為本人本來就拿得到。授權邊界是 API 最貴的一類 bug，而它需要第二組憑證才驗得動，所以這條寫成紀律而不是建議。

上游：人、`test-planning`、`explore` 端點側。下游：`test-data`、`ci-pipeline`、`traceability`、`test-prune`。

## test-data

讓每支測試自己準備、自己清掉它要的資料。

### 設計理念
- **「環境裡本來就有那筆資料」是慢性病。** 它平常都對，直到有人改了那筆資料、或兩支測試同時用它。這種紅最難查，因為程式碼沒動。所以規則直接下在源頭：不依賴既有資料、不共用可變狀態。
- **走 API 建資料，不走 UI。** 用 UI 建前置資料等於把別的功能綁進這支測試的失敗面。登入頁改版，結帳測試跟著紅。API 快、穩，而且失敗訊息指得準。
- **唯一標記是為了平行。** 時間戳＋亂數讓多個 worker 不會搶同一筆，也讓事後在共享環境裡認得出「這是誰建的」。
- **清理放 teardown 而不是測試最後一行。** 測試紅了就跑不到最後一行，於是殘留資料變成下一支的 flaky。失敗會傳染，這是傳染路徑之一。
- **清理失敗要大聲。** 靜默吞掉等於把問題推給下一個人，而且推的時候沒留痕跡。
- **不碰共享環境的核彈鈕。** `reset_shared_env`、`truncate_shared_db` 在 governance 屬 forbidden：它們確實能「清乾淨」，代價是把別人的工作一起清掉。清理只清自己建的東西，這條沒有例外。
- **邊界。** 只提供資料；測試碼要修交 `test-heal`，間歇紅的定性交 `flaky-detect`。

## failure-analysis

一支測試紅了，先歸類根因、再分流，而不是直接動手修。

### 設計理念
- **紅了先別修。** 不知道是 locator drift 還是產品迴歸就修，很容易把測試改爛。先分類。
- **assertion-mismatch 一定過 oracle。** 「預期≠實際」可能是測試過時、也可能是真迴歸。用 `test-oracle` 判「產品該不該這樣」來決定改測試 vs 開 bug，不另造判斷邏輯。
- **依證據判類。** basis 指向 trace/console/network，不憑印象。
- **只分類不修。** 修測試交 `test-heal`、開產品單走 `triage`、flaky 交 `flaky-manager`。
- **一筆的引擎、一批的零件。** `pipeline-triage` 合併根因後每群呼叫本 skill 一次；本 skill 不自己做批次合併。
- **分類表要跟得上介面層。** `locator` 與 `wait-timing` 是畫面專屬的分類，API 測試紅了永遠不會命中它們。少了對應的 API 分類，這些失敗只能落進 `unknown` 或被硬塞進 `environment`，派工就會派錯人：契約漂移該找寫測試的人或後端，憑證過期該找環境，兩者都不是「重試看看」。
- **`contract-drift` 跟 `assertion-mismatch` 走同一個分岔。** 回應結構變了，究竟是契約也改了（測試過時）還是後端改壞了（產品迴歸），一樣不自己猜，交 `test-oracle`。
前身：`pytest-selenium-failure-analysis`。

## flaky-detect

判定一支測試是真的 flaky，還是穩定壞掉。

### 設計理念
- **「flaky」常被當成不想查的藉口。** 一支紅了、重跑過了，就被貼上 flaky 然後放著，但 N 次全紅根本不是 flaky，那是壞了。先把這兩件事分開，才不會讓真 bug 躲在 flaky 標籤底下。
- **重現率是入場券。** 沒有「幾次紅／幾次總數」的 flaky 回報只是印象。有了數字才能排優先序（10% 和 80% 的處置完全不同），也才能追趨勢。
- **不同次紅的原因可能不同。** 所以每次失敗訊息都要留。看起來像一支 flaky，實際上常是兩三個問題疊在一起。
- **N 與門檻讀 config。** 重跑幾次算數、多少 flake_rate 要處理，是每個團隊的 CI 時間預算問題，不是普世常數，不寫死在 skill 裡。
- **禁止用 retry 或 sleep 收尾。** 這兩招都能讓紅色消失，也都讓根因留在原地繼續長大。本 skill 只負責定性；修法交 `test-heal`，驗穩交 `re-run-gate`。
- **全綠也要結案。** 重跑到它紅為止，等於用算力製造證據。不可重現就記 `not-reproduced` 收工。
- **一筆 vs 一批。** 這支定性一支測試；跨 run 趨勢、隔離名單與治理是 `flaky-manager` 的事。

## test-heal

修好「測試自己壞掉」的測試，只改測試、不改產品，嚴禁綠色作弊。

### 設計理念（為什麼這樣設計）
- **綠色作弊是頭號敵人。** 讓測試變綠最快的方法就是把它改爛（skip/放寬斷言/加 retry 蓋時序）。這支 skill 的核心價值不是「會修」，而是「有一份 forbidden 清單擋住作弊」。
- **驗收 = 舊行為下重現紅。** 一支修完只會綠、不會紅的測試，等於沒在測東西。所以硬性要求：對舊/壞行為跑要紅，對現況跑要綠。
- **只吃 test-defect。** product-regression 是產品的錯（開 bug）、environment 是環境（重試）、flaky 是穩定性（quarantine）。這些硬修都是蓋問題。
- **只動測試、不動產品。** 邊界清楚，避免「為了讓測試過而改產品」。
- **批次要人審。** 一次修一片測試風險高，受 governance 授權分級管制。

## re-run-gate

修完測試後，確認是「穩定的綠」才放行；超過上限仍紅就 escalate。

### 設計理念
- **過一次不算修好。** 3 次過 1 是 flaky 不是綠。只認「連續 N 次全綠」。
- **1/N 不是 pass：`test-heal` 綠色作弊的延伸防線。** 「重跑到過為止」一樣是騙綠燈，明文禁止。
- **一定要有停止條件。** 無限重試燒錢又拖延；到 max_retries 就 escalate 交人。
- **埋計量。** 逐次結果寫 `output/<project>/sessions/<date>_<slug>/runs/`，是 ROI 的分母之一，也是 flaky 趨勢來源。
- **只裁決不修。** 再修回 `test-heal`、穩定性問題交 `flaky-manager`。
前身：`re-run-gate`。

## test-prune

決定一支測試該留、該合併、還是該刪。

### 設計理念
- **測試套件只加不減會自己死掉。** 跑得越來越慢、紅得越來越常、於是沒人再認真看紅燈。沒人看的安全網，防護力是零。減法是維護的一部分，不是可選項。
- **判準是「你會不會真的去看」。** 覆蓋率看起來漂亮的測試，如果紅了三個月沒人理，它的實際價值是負的（吃 CI 時間、吃注意力）。
- **刪除不可逆，所以只給建議。** 本 skill 不刪檔、不加 skip，輸出一律 `needs_human_approval: true`。這比照 governance 的 needs_review 精神：副作用越不可逆，授權門檻越高。
- **沒寫清 coverage_lost 就不准建議刪。** 逼出「哪個使用者可見行為之後沒人守」這句話，才擋得住「反正它常壞、刪掉比較清爽」這種懶惰的減法。
- **和 test-heal 的分界必須寫死。** 一支會紅的測試，最快的解法永遠是刪掉它。那是綠色作弊的極端版。所以明文規定：會紅的先走 `failure-analysis` 分流，只有「這個行為已經不需要被測」才輪到本 skill。
- **merge 常常比 remove 好。** 重複覆蓋的兩支，合併後往往保留了雙方的獨有斷言；先問能不能合，再問能不能刪。
