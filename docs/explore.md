# explore/

`skills/explore/` 每支 skill 的設計理由。執行指令在各自的 `SKILL.md`，這裡只寫為什麼。

## exploration-charter

把探索目標談成一份章程（目標/範圍/oracle/邊界），給 explore 用。

### 設計理念

- **從指揮轉成 Mentor 的第一步。** 不再寫「怎麼做」的逐步腳本，改寫「要達成什麼、界線在哪」，路徑留給 agent。
- **user-invoked：動手前先談。** 探索的品質八成取決於章程的好壞，所以由人先把任務談清楚，不讓 agent 自己亂定目標。
- **oracle + out_of_bounds 是讓「放手」安全的關鍵。** oracle 給判斷力、邊界給護欄；兩者缺一，自主探索就會失控或亂喊。
- **甜蜜點：目標明確、路徑開放、界線清楚。** 太細退化成 test case、太空會亂跑。
- **一份章程一個任務。** 存 `projects/<project>/charters/`，可重跑、可人審。
- **`endpoints` 跟 `scope` 分兩個欄位。** 早期的 charter 把「API 授權」當成 `scope` 裡的一個項目，看起來涵蓋到了，實際上 `explore` 讀到的仍然是一個要用畫面去逛的區域名稱，端點層從來沒被直接打過。介面層不同、觀察手段不同、留證的 skill 也不同，欄位就該分開，讓「有沒有真的探索 API」變成看得出來的事。
- **charter 放在哪個專案資料夾，就是打哪個產品。** `explore` 從 `projects/<project>/charters/` 得知 project，再讀同一資料夾的 `config/`。練習站、demo 站可以只有 `charters/`，只帶 `target` 就能跑；有 `config/` 卻缺檔時寧可停手，因為回退讀別的專案會拿 A 產品的 base URL 與帳號去打 B 產品，而且證據看起來完全正常。解析規則見 `references/config-resolution.md`。
- **`auth_context` 要求一個「別人」。** 授權邊界是 API 最常見也最貴的一類 bug，而它需要第二組憑證才驗得動。談章程的時候問，比探索到一半才發現沒帳號好。填 `none` 也可以，但那等於明說這一輪不驗越權。

上游：人。下游：`explore`（吃 charter 自主跑）→ `structured-result` / `classify-anomaly`。

## explore

依 charter 自主探索：自己決定下一步、記路徑、留證，產出候選 findings。

### 設計理念
- **自主的心臟，也是最容易翻車的地方。** LLM agent 放手後三大失敗模式：亂點、鬼打牆、幻覺。本 skill 的價值不在「會點」，而在用三條硬規則把這三件事擋掉。
- **下一步必須引用當前畫面證據** → 防亂點（不能憑空決定）。
- **路徑記憶，做過不重做** → 防鬼打牆。
- **沒證據不喊 bug** → 防幻覺；判定外包給 `test-oracle` / `classify-anomaly`，探索只負責「看與試」。
- **一定要有停止條件。** 達標 / max_steps / 偵測打轉就停，不無限探索。
- **charter 決定邊界。** out-of-bounds 硬守，遇到就停手回報。
- **設定在開跑前解析一次，之後往下傳。** charter 所在的專案資料夾決定讀哪組 `projects/<project>/config/`（規則見 `references/config-resolution.md`）。解析放在迴圈之外，是因為它一輪只該發生一次；解析不到寧可停手也不回退讀其他專案，否則會拿別的產品的 base URL 與帳號跑完一整輪，產出一批看起來很正常的錯證據。

### 覆蓋鐵則怎麼來的

三大失敗模式（亂點、鬼打牆、幻覺）管的是「探索會不會失控」。跑過真實 session 才發現，探索**沒失控但漏看**是另一種失敗，而且更難察覺：探索自己會宣告「charter 範圍走完」，看起來像收工，實際上只覆蓋了三分之二。

2026-08-01 對 academybugs.com 那輪給了難得的校準機會。那站是練習站，站方公告植入 25 支 bug 並自帶確認機制，等於現成的外部判準。對照結果：探索兩輪獨立命中 17 支（召回率 0.68），另外抓到 12 支站方沒計分的真缺陷。判斷力不差，漏掉的 8 支追下去，成因收斂成四個根因。

**根因一：oracle 是相對的，整批一起錯就沒有訊號。**
charter 的 oracle 幾乎都是內部一致性（列表價格等於內頁價格、卡片標題等於內頁標題）。這種判準靠互相比對產生訊號。那輪量了 18 張列表圖，抓到唯一被壓扁的那張，卻漏掉 14 張一致地沒填滿容器的：一致，所以比對無異常，看起來就像設計決定。同一個 oracle 抓得到一個離群，抓不到十四個共犯。
→ 每條相對判準配一條絕對判準。

**根因二：靜態解析取代了互動。**
為了在 `max_steps` 內覆蓋 18 個商品，探索改用 `fetch` 加 DOMParser 比對。便宜、可規模化，但只看得到 HTML 的初始狀態。最能說明問題的是那顆 Twitter 分享鈕：`href` 是完全正常的 `twitter.com/intent/tweet`，屬性檢查一定放行，事件處理器攔截後才改開拼錯的網域。同一排分享鈕上的 MySpace 被抓到了，因為它的 `href` 本身就爛。
→ 靜態解析只用來選目標，不用來下結論。

**根因三：把「動作被接受」當成「動作成功」。**
`checked_and_ok` 裡寫著「編輯表單可載入、可送出」，於是結案。實際上送出後 loader 永遠轉、資料沒存。通過條件停在送出那一刻，沒等終態。
→ 通過條件寫到終態。

**根因四：狀態空間只走單軸。**
每個控制項都在最順手的那個頁面或商品上測一次。色票在 A 商品測、數量在 B 商品測，兩個變因從沒交叉，於是「選特定顏色後加數量會凍住」漏掉。同樣的偏誤讓價格篩選只在列表頁驗過就記成 OK，沒回頭測商品頁側欄的同一組控制項。延伸出來的是可見性問題：收合的元件、主流程沒連過去的頁面，因為 charter 的 scope 寫成功能區塊而非 URL，被隱含涵蓋而整條沒走。
→ 控制項換頁重測、變因交叉配對，並把沒被端出來的東西列進計畫。

### 為什麼停止條件要一起改

這四條鐵則解決的是「漏什麼」，但探索當時並不知道自己漏了。它的 `stop_reason` 寫「charter 範圍走完」，而範圍是自己定義的。沒有外部判準時，「走完」只能是自我宣告，而它的自信來源正是 `checked_and_ok` 那份清單，其中兩條恰好就是根因三的漏檢點。

所以停止條件要求把鐵則自檢的結果寫進 `stop_reason`：說得出哪幾條過了、哪幾條沒過，比宣稱「走完」有用。

### 為什麼要有第二條迴圈，而不是把端點當成一種頁面

畫面側的迴圈靠 `snapshot`：先看有什麼可操作的元素，再從中挑一個。這條迴圈之所以成立，是因為**畫面會主動把可能性端出來**。端點不會。沒有任何請求會告訴你「這個 API 還有 `PATCH` 方法」或「還有一個 `/admin/users`」。

所以端點側的第一步不是觀察，是**列舉**：有契約就照契約列，沒契約就從既有的 network 紀錄反推，並且明說反推出來的清單不完整。把這一步省掉、直接沿用畫面迴圈，結果就是只會打畫面已經打過的那幾個端點，而那批端點通常是最不可能有授權漏洞的一批。

第二個差別是基準。畫面有「正常長什麼樣」的直覺，回應沒有。所以端點側強制先打一次正常請求存起來，後面的每個異常才有得比。少了基準，探索會把「本來就長這樣」記成發現。

上游：`exploration-charter`（給目標與邊界）。下游：`structured-result`、`classify-anomaly`、`bug-verifier`；留證 `evidence-package`（畫面側）／`api-evidence`（端點側）。

## test-oracle

用一致性/規格/對照/使用者期待等 oracle 判斷「這到底是不是 bug」。

### 為什麼 API 要另開一張 oracle 表

不是因為 API 比較特別，是因為**畫面層的三條免費 oracle 在 API 上會失效**。沒有畫面就沒有「同一畫面自相矛盾」，沒有瀏覽器就沒有 console error，而「API↔UI 一致」這條在只有 API 的情境下沒有另一半可比。剩下的若只有規格 oracle，等於沒有 spec 就什麼都判不動，探索會整批卡在 `needs-spec`。

補上的那幾條，共通點是**判準內建在協定或在回應自身**，不必外求：HTTP 狀態碼有公認語意、同一個 API 的錯誤結構該長一樣、宣告冪等的方法重打該同結果、換個 id 不該拿到別人的資料。它們補回「不需外部資訊」那一格，強度才跟 UI 情境對得起來。

### 契約 oracle 為什麼排在後面

schema 符合是很好判的 oracle，但它需要一份 OpenAPI，而**契約本身也可能是錯的或過期的**。契約說回 `200`、實際回 `200` 但語意荒謬，契約 oracle 會判過。所以排序上讓不靠外部檔案的幾條先跑，契約當補強而不是唯一判準。契約來源填「無」時直接停用它，不允許用「我覺得該有這個欄位」冒充 schema。

### `4xx` 的陷阱

API 探索最常見的假 bug 是把 `400` 與 `401` 當成發現。那通常是產品正確地拒絕了亂打的請求。真正要判的是兩個方向的錯：該擋沒擋（越權拿到資料、非法值被接受），與該過卻擋（合法請求被拒）。`429` 則先當自己打太快，對照 `product-context.md` 記的速率限制再說。
